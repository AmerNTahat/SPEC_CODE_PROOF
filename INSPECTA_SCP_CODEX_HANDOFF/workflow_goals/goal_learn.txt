Title: Learn full-stack Meta-Rules for continuing, completing, extending, repairing,
and optionally creating HAMR-compatible systems with scoped structural preservation

Revision: 2026-09-22 / integrated-handoff-v2.0
Status: Revised implementation goal; not a claim that the Workbench is implemented.
Target path: SCP-extention-artificats/isolette_io_extnded/goal_learn.txt
Companion: goal_user.txt from the same revision.

Read this first
==============

Upgrade the existing SCP learning workflow, not merely its documentation. Preserve
historical DASC artifacts and original rule releases in version control. This goal
replaces the process-fragment-only emphasis of the older goal while preserving its
rich linguistic rules, full-stack context, confidence forecasts, verification
requirements, memory isolation, and bounded repair.

The primary outcome is an approved full-stack rulebook library that helps perform
the user's requested engineering work on either an existing codebase or a new
system. Learn reusable linguistic, specification, implementation, proof, testing,
and repair patterns from approved materials, examples, and interactions.

Creation from scratch is an OPTIONAL capability, selected only when the user
requests it or explicitly approves a declared creation experiment. It is not the
default operation and must not replace an existing application as a shortcut.
When the user supplies a codebase and asks to continue, complete, extend, repair,
or verify it, use the authorized existing artifacts as the starting point. These
may include SysML/AADL, GUMBO, implementation, proof support, tests, and build files.

The deliverable is determined by the approved task scope. An implementation-only
completion may preserve its existing model and contracts; a proof repair may leave
executable behavior unchanged. An explicitly requested whole-system creation must
produce all requested connected artifacts, not merely a fragment or recommendation.
A scoped task may finish without claiming the entire codebase is complete.

Core invariant
==============

Match the preservation policy to the task. For reconstruction against a reviewed
reference, check structural equivalence under ONE consistent, scope-aware role
correspondence, allowing only the internal renaming authorized by that task. For
continuation/completion/repair, preserve existing correct archetypes, names, public
interfaces, behavior, and unaffected relationships. Check requested additions or
corrections under an explicit change contract, not literal equivalence to an
incomplete or defective starting project. For extension, verify the approved delta
and unaffected structure. With no unique reference, check source-backed conformance.

Equivalence modulo renaming is a checker capability, not permission to rename an
existing codebase. Do not freeze a known defect merely to preserve the baseline;
record the defect and the approved correction. Required categories, ownership,
connections, properties, and contractual responsibilities cannot change silently.

A high cosine score, similar names, successful parsing, or an agent's assertion of
equivalence is not evidence that this invariant holds. The trusted evaluator must
check it and save a mapping witness plus differences and limitations.

Structural equivalence is scoped architectural evidence, not a blanket claim of
behavioral equivalence. Requirements, GUMBO fidelity, implementation, proofs, and
tests have separate gates.

1. Shared operating rules
=========================

Execution:
Use the Workbench controller shared by CLI and UI. Ordinary code owns tool calls,
permissions, snapshots, budget accounting, checks, and evidence. Astra owns explicit
knowledge extraction, interpretation, ambiguous selection, generation, and repair
proposals. Do not ask an agent to declare its own output accepted.

Models:
Use GPT-family models only. Astra is the primary configured model. Resolve its
available identifier through the actual installation; do not invent an identifier.
No Chinese models, third-party embedding/reranking models, Jev dependency,
fine-tuning, or small-model deployment is required in this implementation.

Toolchain:
Follow the consolidated Workbench installation goal. Reuse Loonwerks/KSU-supported
installers and the reference/current-validated environment design. Discover current
Sireum and Codex CLI versions at setup, test compatibility, then pin the selected
versions, libraries, model profile, and worker image digest for the run. Missing
checks block affected acceptance; do not replace them with agent judgment.

Paths:
Resolve the selected project, materials, library roots, reference roots, and outputs
from the approved project configuration. Do not assume a personal absolute path or
an IDE. Shared base libraries are read-only. Preserve the existing rule-books/ and
eva-results/ conventions under the configured project/output root.

Reporting:
Use headings and labeled fields on separate lines, not wide Markdown tables.
Report implemented code, performed checks, recorded outcomes, and blockers
separately from plans, mock fixtures, or recorded demonstrations.

2. Configuration and budgets
============================

workflow_mode:
learning

task_operation:
auto by default, meaning inspect intent and authorized inputs, NOT permission to
create or change arbitrary artifacts. Resolve the actual operation before writing:
continue-project, complete-system, extend-system, repair-system, verify-only, or
create-system. Continue-project is the conservative route for a supplied codebase
and a request to continue; record the specific authorized next steps. An empty
folder or absent SysML file does not by itself authorize create-system.

create-system:
Requires an explicit user request or approved benchmark/task configuration. Create
the new application in a separate empty target workspace; do not delete or replace
an existing project to make it appear to have been generated from scratch.

mixed_scope:
A task may preserve its architecture, complete GUMBO, implement missing code, and
repair a proof within the same approved scope. Record per-artifact actions and
stage dependencies rather than forcing a full rebuild of every layer. Creating a
missing file inside an existing project is completion, not whole-system creation.
A scoped exercise cannot be reported as whole-system success.

assistance:
automatic by default, or interactive. Automatic experimentation is limited to the
approved development scope. Publishing a release, broadening approved scope,
changing source requirements, or increasing budget requires human approval.

learning_materials:
User-selected directory containing permitted manuals, English/formal pairs, code,
proofs, tests, tool references, and approved human/agent repair episodes.

development_validation:
Separate task collection used to test and refine rules and policies.

final_evaluation:
Protected task collection evaluated only after the release and policy are frozen.
References and final evaluator results cannot guide repair or rule promotion.

architecture_policy:
reconstruction-equivalence, approved-change, or new-design-conformance.

naming_policy:
preserve-existing by default. Bind learned abstract roles to the names already
used in the supplied codebase. Choose names only for new entities, following the
project's conventions. consistent-internal-renaming is enabled only for an approved
creation/reconstruction naming policy or an explicitly authorized rename/refactor.
External interfaces, imported library symbols, stable requirement IDs, and ABI or
configuration names stay fixed unless a coordinated change is approved.

learning_time_limit:
60 minutes initial default; configurable.

learning_token_limit:
3,000,000 aggregate model tokens initial default; configurable.

repair_limits:
5 attempts per issue; 20 across the run; one concurrent model call initially.

validation_reserve:
Reserve 20 percent of the wall-clock allowance for required final checks and
packaging. This is a limit policy, not an estimate of completion time.

Enforcement:
All extraction, confidence assessment, generation, repair, selection, retries, and
subagents share the parent budget. Normalize actual usage without double-counting
cached-input or reasoning subclasses. Verification and architecture search also
have timeouts. Missing usage is unknown, not zero. Strict token mode must fail
closed when the selected execution adapter cannot enforce its claimed ceiling.
Do not silently fall back to an unbounded adapter.

At exhaustion:
Stop new work, cancel where supported, preserve provisional progress, and record
unfinished checks. A comparison timeout is UNKNOWN, not equivalent and not proof
of non-equivalence. Resuming preserves cumulative usage unless new allowance is
explicitly approved. Keep the historical DASC budget as a separate profile.

4. Construct a leakage-controlled learning curriculum
=====================================================

For each task, record:
Task and family ID, source passages, source role (requirement/example/manual),
source revision, resolved task operation and its authorization, starting-workspace
manifest, system boundary, selected root, target profile, allowed libraries and
existing code, permitted examples, reviewed design choices, requested changes,
protected files/relationships, required artifacts, naming/architecture policy,
behavioral obligations, comparison scope, known pre-existing failures, and evaluator
data. Include tracked and relevant untracked/modified files without importing secrets.

Continuation/completion episodes:
Use the actual authorized starting codebase, including partial or complete models,
existing application/proof/test files, generated interfaces, and configuration.
Prepare an isolated candidate snapshot of those inputs; do not empty or rebuild it.
A commit ID alone is insufficient when authorized uncommitted work exists. Record
exact file content hashes and preserve user changes. Compare the requested delta
and affected checks against a baseline that records PASS/FAIL/UNKNOWN/NOT_RUN.
A baseline inspection failure is not permission for wholesale replacement.

Learning curriculum:
Include continuation, targeted completion, extension, cross-stack repair, and
verification tasks alongside explicitly selected from-scratch creation tasks.
Learn how to recognize existing valid patterns, locate gaps, reuse APIs and proofs,
bind old rule parameters to existing names, and avoid duplicating components.
A suite may exercise all operations; that does not force them into every run.

Use independent source families for final transfer where possible. Keep renamed
variants and descendants of a source example in the same lineage group. Monitor to
Regulate remains an intra-system experiment; do not relabel it broad transfer.
Audit prior exposure before labeling a task pipeline-held-out.

Blank-project construction means (create-system tasks only):
The generator starts with English/context inputs, approved general rule releases,
permitted source examples, and base tool libraries. The target's complete or partial
SysML, target AADL solution, generated AIR, generated application, archived answers,
and architecture-bearing scaffolds are absent from its accessible workspace.
Empty package stubs are unnecessary and, when used, must be declared as scaffolding.
Base library definitions and general parameterized patterns are allowed.

Two different learning uses of references:
During extraction, a permitted solved source example may be read and analyzed.
During a development reconstruction episode, keep that target's answer outside the
generator workspace and compare only the frozen candidate. For a completion/repair
benchmark, supply the declared initial codebase, but keep the withheld final patch
or completed answer outside the generator workspace. Existing authorized input code
is not answer leakage merely because it contains a target component. Do not strip
that legitimate input under a blanket 'no target artifacts' rule.
Reference-derived feedback may inform development revision, but record that
intervention and cost. This is supervised development, not an untouched final test.

Final evaluation:
Use a fresh session and frozen release. Permit ordinary project tool diagnostics
according to the experiment policy, but do not reveal hidden reference models,
mappings, reference-specific differences, scores, or oracle tests for iterative
repair. Score the committed result and publish the final evaluation afterward.

Underdetermined descriptions:
Exact architecture reconstruction needs source-provided or independently reviewed
architectural decisions. When English permits several valid designs, either obtain
those decisions or label the task conformance-based. Do not penalize a legitimate
alternative solely for differing from one unspecified reference, and do not reveal
the answer architecture disguised as general context.

5. Extract full-stack linguistic and reasoning patterns
=======================================================

Ask these questions for EACH approved example or meaningful interaction:

Meaning and source:
What source passage supports the pattern? Is it normative, explanatory, a worked
example, human rationale, or model inference? What phrase activates the pattern?
What actor, action, object, modality, quantifier, condition, boundary, exception,
time dependence, or previous state must be represented? What is still unknown?

System construction:
Why does the description imply a system boundary, process, thread, device role,
interface, or data type? Which boundaries are required rather than incidental?
How are reusable component definitions distinguished from their instances?
Which dependencies and initialization order are required to assemble the whole
system? How do fan-out, containment, connection paths, and bindings compose?

Language-to-formal choice:
What phrases suggest input/output, data/event/event-data, state retention, mutually
exclusive cases, or necessary versus sufficient conditions? Give positive
paraphrases and a misleading near-match. Explain why the selected interpretation
fits; do not use blind keyword replacement.

Names and identity:
Which identifiers are incidental and parameterizable? Which names are externally
fixed? What typed roles do variables, ports, processes, and threads represent?
How will every bound role have one consistent target identity across all files?

Existing-codebase continuation:
What already satisfies the requested requirement, and what evidence supports that?
What is missing, defective, or intentionally to be changed? Which existing APIs,
contracts, tests, proof lemmas, marker regions, conventions, and build procedures
should be reused? What is the smallest justified change? Which failures predate this
run? How does a candidate addition fit the approved architecture without duplicating
an existing role? Which files must remain byte-for-byte unchanged, and which must
preserve their interface or behavior while allowing approved edits?

Code and proof:
How does the model map to generated APIs, application code, contract obligations,
initialization, state updates, invariants, proof cases, or helper lemmas? Which
files are generator-owned? What constitutes a justified proof repair rather than
weakened assumptions or bypassed verification?

Testing and diagnostics:
What positive, boundary, negative, and stateful tests distinguish correct behavior?
What can a generated oracle fail to check? Where was a failure observed, where was
its cause, and what human/agent repair resolved it under real tool checks?

Transfer and scope:
What is the reusable engineering principle? What parameters vary across systems?
Under what tool/profile/version conditions does it apply? When should it not apply?
What unchanged obligations must survive application or repair?

Budget:
What minimal experiment can distinguish the alternatives? What is its predicted
cost, and what budget is left for required checks? Do not verbalize after every
routine command; focus on informative examples, corrections, and verified repairs.

Add:
Typed semantic roles; actor/object/condition relationships; positive paraphrases;

Never mark a template tool-valid because it looks plausible. Exercise its actual

Library views:
System-construction and archetype composition.
Existing-codebase comprehension, completion, extension, and minimal-change patterns.
English interpretation and semantic/specification patterns.
Processes, threads, ports, connections, scheduling, and bindings.
GUMBO behavior, state, initialization, integration, and ownership.

Cross-stack mapping and traceability.

One record per rule identity:
Specialized books and the combined cross-stack book are generated views of the

Confidence:
Ask Astra how strongly it believes the book will succeed given the material and
context it has seen. Record that original forecast, question, context, model, scope,
and revision before evaluation. Assess a combined book directly, not by averaging
individual scores. Show observations separately. Never treat confidence as a gate.

7. Apply learned patterns according to the selected operation
============================================================

A. Resolve intent, authorized inputs, operation, deliverables, and protected scope.
   Save operation-plan.json, input-workspace-manifest.json, and change-scope.json.
   Do not reinterpret a continuation request as a whole-system reconstruction.
B. For an existing project, inventory and snapshot the actual authorized codebase.
   Preserve dirty/untracked user work; do not reset, clean, or overwrite the source
   workspace. Run only safe, budgeted baseline checks through the trusted controller
   and record known failures, unavailable tools, and stale evidence separately.
C. Reuse or derive the source-backed requirement ledger and architecture obligations
   for the requested scope. Do not invent missing English intent. Retain existing
   IDs, tests, proofs, APIs, and names unless an approved change requires otherwise.
D. Bind applicable rule roles to existing entities first. Identify justified missing
   entities and duplicate-risk checks. Inspect context before paid generation.
E. Choose the operation route:
   continue-project: perform authorized unfinished work in the existing workflow;
   complete-system: add the declared missing model/contract/code/proof/test pieces;
   extend-system: implement a reviewed feature/change and preserve unaffected scope;
   repair-system: fix the diagnosed defect with the smallest justified edits;
   verify-only: run approved checks in an isolated copy without changing source;
   create-system: ONLY when explicitly requested, construct the new application from
     approved English/context, libraries, and rules without a target solution.
F. Execute only the stages required by that route and their dependencies. An
   implementation completion with an unchanged valid model should not re-synthesize
   SysML or GUMBO. Run normal generation when a declared dependency, model change,
   or absent/out-of-date generated artifact requires it. Respect file ownership.
G. Construct or update requested artifacts. For authorized create-system tasks,
   assemble required roots, packages, types, definitions, instances, ports,
   connections, properties, GUMBO behavior, and requested downstream code/proofs.
   For continuation tasks, preserve supplied architecture and valid behavior while
   making only the approved additions, repairs, or extensions.
H. Run relevant parsing, HAMR subset, requirement, architecture, rename-consistency,
   testing, proof, and build gates under the declared acceptance policy. Check the
   full affected dependency closure; do not demand a new-system build for an
   unrelated scoped task or waive required integration checks after a shared change.
I. Compare the result to the approved source/change policy and to the starting
   snapshot. Report pre-existing failures and new regressions independently.
   No regression is excused simply because the starting project was incomplete.
J. Record exact changes, unchanged-scope checks, actual results, cost, and unknowns.
   Apply a reviewed patch/promote a candidate without overwriting intervening user
   edits. Changed source hashes require reconciliation, not an automatic reset.

Completion status is scope-aware:
A task can satisfy its declared acceptance policy while the larger project has
separately reported unresolved issues, but the agent cannot waive those issues or
change the policy retroactively. Never label full-system acceptance unless every
required system-level obligation and gate passes. A source-only requested change
must not imply code/proof completion. A required blocker remains a blocker.

Use exact syntax from the pinned profile. A source or code example is evidence, not
permission to redesign the system. Non-behavioral obligations need their own checks;
not every requirement belongs in GUMBO. Missing intent requires review or a scoped
stop, not invented behavior to obtain a passing checker result.

8. Structural equivalence modulo consistent internal renaming
=============================================================

Implement a dedicated deterministic checker. Keep protected reference data read-only
in the trusted evaluator; authorized existing project data remains available for
continuation work. A candidate-provided mapping is a proposal, not proof.

Operation-aware scope:
For equivalent reconstruction, compare the full declared reference scope. For
completion or extension, check the approved additions/changes and preservation of
unaffected archetypes and obligations. A missing element in an incomplete baseline
may be added when required; it must not fail solely for being new. A defective
baseline element may be corrected within the approved change. For verify-only,
report the current state without repairs. When no architecture is present and the
requested task does not require creating one, do not invent SysML or claim a
structural equivalence check was performed. Name-preservation is the default for
existing entities. Run equivalence-under-renaming only within authorized scope.

Local similarity:
Use model-free token-vector cosine and corrected text-difference utilities for
retrieval and diagnostic comparison. Specify preprocessing and zero-vector cases;
preserve operators, numbers, units, negation, and typed role information. Label
lexical cosine separately from neural embeddings and semantic equivalence. Do not
make API calls or silently load another model for this default local check. A
consistent rename may lower lexical similarity without changing architecture;
that alone must not reject an otherwise valid mapped result. Keep retrieval,
absolute distance, and relative-improvement thresholds as distinct settings.

Comparison basis:
A reviewed reference, root configuration, profile, comparison policy, and source
role ledger. Build both a resolved declaration/ownership view and an instantiated
architecture view. Keep required declarations even when they are absent from an
instantiated deployment. Do not infer preserved containment from a flattened graph.

Cross-language basis:
When the task compares SysML against AADL, use validated frontend adapters and an
explicit semantic normalization profile. HAMR has a shared intermediate
representation, but that fact alone does not implement an equivalence checker.
If the available IR omits a required property, obtain it from the resolved source
or report the comparison UNKNOWN. Never silently ignore missing information.
Normalize an AADL component type plus its selected implementation and a SysML
component definition into corresponding logical interface/implementation roles
where a validated adapter permits it. Do not require raw AST node counts to match
across languages. Preserve provenance back to every relevant source declaration.

Normalization:
Allow ordering, comments, consistently renamed internal identifiers, scope-safe
package renaming, and exact equivalent unit representations only as explicitly
permitted. Resolve inherited/default properties and declaration references.
Do not erase categories, roles, containment, direction, type structure/ranges,
units, queue semantics, state ownership, multiplicity, deployment properties, or
required connections merely to obtain a match.

Correspondence:
Find or validate a one-to-one mapping within each compared entity category and
scope. It must be globally consistent across the model. Preserve each required
component archetype, source-linked role, definition/instance relationship, owner,
port kind/direction/type, edge kind and multiplicity, ordering when meaningful,
critical property, and contract attachment. Every required reference element must
be mapped, and every candidate architectural element must be accounted for.

For a required edge u --relation--> v in the normalized reference, the corresponding
edge f(u) --relation--> f(v) must exist in the candidate, and conversely within the
equivalence scope. For approved additions/removals, use a checked partial mapping
for preserved entities plus a separate explicit delta; do not force a bijection
between an incomplete baseline and its approved completion. Required absence
constraints must still hold. A renaming cannot
merge two different roles, split one component, swap upper/lower limits, or bypass
an interface. An equal component/port count does not establish equivalence.

Semantic role anchors:
Use reviewed source roles and actual structural/behavioral evidence, not only
candidate-supplied role labels. Structurally identical nodes with different
requirement responsibilities are not freely interchangeable. A genuine symmetry
may allow several equally valid mappings; report that ambiguity. If an unresolved
mapping affects correctness, require review and withhold a definitive pass.

Whole-project consistency:
All declarations, uses, connections, type references, GUMBO references, root config,
code-generation settings, generated APIs, developer code, tests, proof annotations,
and trace links must resolve consistently after a rename. Regenerate generator-owned
artifacts through HAMR; do not perform unsafe global string substitution.
Requirement IDs remain stable while display names may change.

Scope boundaries:
Do not rename imported library symbols, external ABI names, or public interface
contracts unless explicitly allowed. Flattening, splitting a process, changing a
port kind, or changing a deployment profile is an architectural transformation,
not a rename. Use an independently approved transformation/refinement contract,
not the strict-equivalence label. Do not silently strip generated monitor nodes;
account for them in a documented view/transformation if present.

Behavioral boundary:
Contract owner/signature/reference consistency is part of structural checking.
Contract formula equivalence is a separate obligation. A bound-variable rename
can be checked with scope-aware expression normalization when supported; arbitrary
formula rewrites require appropriate proof/testing evidence. Equal architecture
does not establish equal behavior, timing semantics, or specification fidelity.

Checker result:
PASS, FAIL, or UNKNOWN with reason, supported scope, reference/candidate hashes,
profile/normalization version, declaration and instance mapping witnesses,
missing/extra/changed elements, ambiguous mappings, source-linked role evidence,
rename-consistency findings, counterexample differences, and elapsed cost.
Use FAIL for a concrete violated invariant; use UNKNOWN for unsupported scope or
exhausted search. A hash, high F1, or isomorphism on an untyped graph is insufficient.

Evidence files for each checked candidate:
architecture-comparison.json
architecture-correspondence.json
rename-consistency.json
source-to-model-trace.json

9. Validate the checker with deliberate positive and negative cases
===================================================================

Positive tests:
Consistently rename all allowed internal identifiers, including processes, threads,
ports, and private types; regenerate code and check all references.
Reorder declarations without changing meaning.
Change exact unit notation only where the policy permits exact normalization.
Test multiple instances of the same definition and legitimate structural symmetry.

Negative tests:
Rename a declaration but leave a stale use or GUMBO reference.
Introduce a name collision or wrong namespace binding.
Swap same-typed upper/lower limit ports or alarm/heat-control roles.
Remove a connection, add a bypass, or change connection multiplicity.
Move a thread to another process or change its AADL/HAMR category.
Change data/event/event-data semantics, period, domain, or binding.
Attach a correct-looking contract to the wrong owner.
Delete a required declaration not visible in the flattened instance model.
Weaken a guarantee or strengthen an assumption: structure may pass, but acceptance
must fail or require review under the independent fidelity/proof policy.
Present unsupported syntax or deliberately exhaust the comparison budget.

Do not test only the same data structure produced by the checker implementation.
Use hand-reviewed fixtures, actual parsed variants, and independent expected results.
Passing synthetic checker tests does not claim a real SysML/HAMR run succeeded.

10. Use feedback to generalize, specialize, and learn reusable repairs
=====================================================================

For each failure, record the observed tool/stage, raw diagnostic, normalized
signature, suspected cause, affected obligation, permitted repair location, and
protected structure. A proof diagnostic may originate in specification, code,
proof support, or environment; locate the cause before editing.

Retrieve eligible repair patterns using tool/profile constraints, diagnostic
features, local cosine, and structural context. Ask Astra when selection remains
ambiguous. Similar wording alone does not establish the same cause. A retrieved
pattern must be rebound to current semantic roles and names.

Generate repairs in separate candidate snapshots. Keep the last accepted snapshot
and separately resumable provisional progress. An intermediate repair need not
pass every final gate to be retained as development progress; it may never be
reported as final acceptance. Repeated identical failed repairs trigger stop or
escalation rather than an uncontrolled loop.

A human correction or agent repair becomes a candidate episode. Only actual
validation and transfer evidence support promotion. Store unsuccessful applications
and scope counterexamples as well as successes. Do not blame a rule for a missing
tool installation without classifying the environment failure separately.

Generalize principles, not incidental identifiers; specialize when interface,
target, or proof semantics require it. Keep a deterministic applicability filter
before optional model-based selection. Search budget and repair budgets are shared.

11. Retention, meta-learning, and release isolation
==================================================

Use support/query development episodes to compare extraction and selection policies.
A policy can change questions, abstraction granularity, relevance features, context
size, or the order of discriminating checks. Use separate query tasks to measure
whether its learned rules help beyond the examples used to derive them.

A rule is eligible for approval only with documented source support, tested scope,
applicability/counterexamples, required real tool results, structural evidence for
reconstruction tasks, and an acceptable regression/transfer assessment. No single
cosine threshold overrides missing architecture, coverage, or proof evidence.

Publish one immutable release with structured records, combined/specialized views,
approved minimal examples, prompts, tested deterministic procedures, confidence
